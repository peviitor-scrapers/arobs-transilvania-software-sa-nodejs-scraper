# Commit checklist

Quick checklist for pushing to `main` directly (this repo has no PR
workflow — `main` is protected only against force-push/deletion, not
against direct pushes). Run through this before every push, not just the
big ones; most of the bugs this template has hit so far were small,
easy-to-skip steps like these.

## Before every push

- [ ] **Run tests locally** (`pytest -q` / `npm test`) — don't rely on CI to
      catch it first. CI failing on `main` means every scheduled run after
      it is red too, not just your push.
- [ ] **`git status` before `git add`** — check what's actually staged,
      especially after a broad edit. Never commit `.env`, API keys, or
      anything `.gitignore` is supposed to catch but might not (verify a
      new file type is actually ignored before assuming it is).
- [ ] **Don't hand-edit `company.json` / `docs/jobs.md` / `docs/company.json`
      across more than one sitting.** The scheduled scrape workflow commits
      to these files automatically (`[skip ci] Update scraped jobs`). A
      long-lived local edit on top of them is exactly how a real merge
      conflict happened on this fleet before — `git pull` right before you
      start, and push the same day.

## When the change touches behavior (not docs-only)

- [ ] **Bump `CHANGELOG.md`** — new `## [x.y.z] - YYYY-MM-DD` heading at the
      top, Keep a Changelog style (`### Added` / `### Fixed` / `### Changed`).
      Explain *why*, not just what — the next person reading it (including
      future-you, or an AI agent working from this file) should understand
      the reasoning without re-deriving it from the diff.
- [ ] **Bump the version field to match** — `package.json` (Node) or
      `pyproject.toml` (Python). The Node side has a test
      (`tests/consistency/version.test.js`) that fails the build if these
      drift; treat the same rule as binding on the Python side even without
      an enforced test yet.
- [ ] **Commit message prefix** — match what this fleet already uses:
      `fix:`, `feat:`, `refactor:`, `ci:`, `chore:`, `docs:`. Consistent
      prefixes are what make `git log --oneline` actually useful for
      scanning history later.

## If `git push` is rejected

- [ ] `git pull --no-edit` first, resolve any real conflict, then push
      again. **Never `--force` to main** — it's blocked by branch
      protection anyway, and if you ever push to a fork/branch where it
      isn't, force-pushing over someone else's (or a scheduled workflow's)
      commit is how work gets silently lost.
- [ ] A conflict in `company.json` / `docs/jobs.md` against an incoming
      `[skip ci]` commit is almost always safe to resolve by keeping the
      remote/CI version — that data is regenerated by the next scheduled
      run regardless. A conflict anywhere else needs an actual look before
      picking a side.

## Template-specific

- [ ] If the fix belongs in `scrape.yml`/`tests.yml` logic and this repo
      calls a `*-reusable.yml` from Brewtality-3-16 (check for `uses:
      peviitor-scrapers/Brewtality-3-16/...` in the workflow file) — the fix
      probably belongs in the **template's** reusable workflow, not a
      one-off patch here. A patch here only fixes this repo; a fix in the
      template reaches every derived scraper on its next scheduled run.
